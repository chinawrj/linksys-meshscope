# MX4200 MQTT control and custom-IMG feasibility

Analysis date: 2026-07-28

This is an offline analysis of the official MX4200 v1 images
`1.0.13.210200` and `1.0.13.216903`. No request was sent to a router and no
image was flashed.

## Conclusions

1. **MQTT control is feasible after a privileged bootstrap.** Changing the
   broker ACL can expose the existing `network/<child UUID>/BH/config`
   consumer directly to a LAN MQTT client. An ACL change cannot create new
   operations: it only grants access to Topic consumers already implemented
   by the firmware.
2. **Changing the stock anonymous ACL is not an acceptable production
   design.** Adding the Parent-steering Topic to port 1883 would let every LAN
   client steer every Node. A dedicated authenticated, encrypted listener
   with a narrow ACL is the defensible direct-MQTT design.
3. **A modified OEM-style IMG can be built and passes the stock updater's
   offline validation.** A proof image based on `1.0.13.216903` contains the
   verified Dropbear payload, an idempotent SSH service, and one public key.
   The stock `/usr/sbin/fwcc verify_signature` accepted it.
4. **Updater acceptance is not hardware boot proof.** NAND geometry, the
   exact hardware revision, inactive-slot selection, firewall behavior, and
   bootloader recovery still require read-only inspection and a controlled
   physical test.

The proof image, its private key, extracted firmware, and generated UBI are
all ignored by Git. They must not be published as a generic firmware build.

## MQTT architecture

The Mosquitto configuration and authentication plugin are byte-identical
between `210200` and `216903`. The broker is Mosquitto `1.6.2` and runs only
on the Master.

| Listener | Binding | Authentication | ACL |
| --- | --- | --- | --- |
| `1883` | Master `br0` address | Anonymous | `/tmp/etc/mosquitto/strict.acl` |
| `1883` | `localhost` | Anonymous | No ACL restriction |
| `8883` | All configured addresses | TLS-PSK plus messaging username/password | Authentication plugin allows the authenticated connection |

`per_listener_settings true` makes those settings listener-specific.
`service_mosquitto.sh` copies `/etc/mosquitto` to
`/tmp/etc/mosquitto` whenever the service starts and substitutes the live
address, ports, and PSK. Consequently:

- editing `/tmp/etc/mosquitto/strict.acl` is temporary;
- restarting Mosquitto restores the rootfs copy;
- there is no `syscfg` variable that selects `strict.acl`, `moderate.acl`, or
  `open.acl`; and
- a persistent ACL change requires a rootfs change or a privileged boot hook.

The bundled Mosquitto readme describes Node steering as a dangerous command
that is deliberately excluded from `strict.acl`. The current ACL does not
grant anonymous writes to:

```text
network/+/BH/config
```

### Secure listener behavior

The secure listener uses:

```text
psk_file /tmp/etc/mosquitto/psk/server.keys
auth_plugin /lib/libnodes_psk_auth_plugin.so
```

Its credentials are internal mesh values, not the local web administrator
password:

```text
omsg::psk_id
omsg::psk
smart_connect::auth_login
smart_connect::auth_pass
```

Disassembly of `libnodes_psk_auth_plugin.so` shows:

- username/password authentication is delegated to
  `sc_authenticate_login_pass`;
- PSK retrieval is implemented by `mosquitto_auth_psk_key_get`; and
- `mosquitto_auth_acl_check` returns Mosquitto success after optional debug
  logging, so an authenticated mesh client is not restricted by Topic.

This means port 8883 can already carry the Parent request if the legitimate
internal credentials are available. Those credentials should not be exported
to a browser or reused as MeshScope credentials.

## What an ACL change can expose

The firmware's subscriber files define the API surface. Examples include:

- exact backhaul selection: `network/<UUID>/BH/config`;
- automatic-channel configuration: `network/<UUID>/AC/config`;
- firmware-update commands;
- WPS and setup events; and
- client- and Node-steering events.

An ACL line grants transport access to one of those consumers; it does not
turn MQTT into a general `syscfg`, shell, JNAP, or SSH API. In particular,
there is no MQTT consumer that installs or enables an SSH daemon.

### Exact Parent request

The narrow ACL entry would be:

```text
topic write network/+/BH/config
```

The exact payload generated by the stock `mk_infra_payload` was executed under
the firmware's own Lua runtime. Its shape is:

```json
{
  "uuid": "CHILD-DEVICE-UUID",
  "type": "set",
  "TS": "CURRENT-UTC-TIMESTAMP",
  "data": {
    "band": "5GL",
    "bssid": "02:11:22:33:44:55",
    "channel": "36"
  }
}
```

The Topic's UUID selects the subscriber. The payload should carry the same
UUID. `service_node-mode.sh` validates the channel, BSSID, and band, writes
the runtime backhaul selector state, and triggers the reconnect.

Opening the Topic does not remove the safeguards required by MeshScope:

- resolve BSSID and channel from fresh trusted DEVINFO;
- reject self, current Parent, wired targets, and descendants;
- serialize mutations;
- capture the previous tuple;
- observe the resulting Parent; and
- perform at most one rollback.

## ACL implementation choices

### A. Add one line to `strict.acl` — works, unsafe

Adding the one write rule to the stock port-1883 ACL was tested using the
firmware's ARM Mosquitto binary under QEMU:

- a QoS-1 publish to `network/child-uuid/BH/config` was accepted;
- a publish to `network/child-uuid/AC/config` was denied with MQTT reason
  `0x87`; and
- the broker remained anonymous.

This proves the minimum mechanism, but it grants every device on the LAN the
same steering authority. It is suitable only for an isolated lab.

### B. Use the stock 8883 listener — encrypted, but over-privileged

The existing TLS-PSK listener needs the mesh PSK and messaging
username/password. Its authentication plugin then permits all Topics. It
requires no ACL change, but exposing those credentials to MeshScope gives the
application broader authority than Parent steering requires.

### C. Add a dedicated MeshScope listener — recommended direct-MQTT design

A separate listener should have:

- a unique port;
- TLS with a MeshScope-specific client identity;
- `allow_anonymous false`;
- a source-IP firewall allowlist;
- a dedicated ACL containing only required read/write Topics; and
- credentials stored outside the browser.

The minimum ACL is:

```text
user meshscope
topic write network/+/BH/config
topic read network/+/BH/status
topic read network/+/DEVINFO
```

The password-plus-ACL part of this design was tested with the stock ARM
Mosquitto binary:

- an unauthenticated connection received CONNACK `Not authorized`;
- the `meshscope` account could publish `BH/config`;
- the same account was denied on `AC/config`.

That test used loopback and a throwaway password. A physical deployment must
add TLS and verify the firewall before binding a new listener to `br0`.

For MeshScope, a narrow on-router helper reached through SSH remains simpler
to audit than giving the application permanent MQTT credentials. Direct MQTT
is nevertheless technically viable.

## Custom IMG proof

### Base image

| Field | Value |
| --- | --- |
| Firmware | MX4200 v1 `1.0.13.216903` |
| Original SHA-256 | `b0a954835c879822fd1a2da23f09a6ec37da69914aacf07d8038b06fa02fad25` |
| Original size | 38,404,096 bytes |
| UBI offset | `0x600000` |
| Original UBI PEBs | 244 |
| PEB / LEB | 131,072 / 126,976 bytes |
| Minimum I/O | 2,048 bytes |
| UBI sequence | `1903991695` |
| Volume | ID 0, dynamic `squashfs`, autoresize |
| Reserved LEBs | 603 |

The first `0x600000` bytes contain the original FIT kernel and DTB. They were
preserved byte-for-byte. The Linksys footer occupies the final 256 bytes of a
one-PEB `0xFF` trailer.

### Injected files

The proof rootfs adds:

```text
/usr/sbin/dropbearmulti
/usr/sbin/dropbear -> dropbearmulti
/usr/sbin/dropbearkey -> dropbearmulti
/etc/init.d/service_sshd.sh
/etc/meshscope-ssh/authorized_keys
```

The Dropbear binary is the previously verified 247,784-byte ARM/uClibc build:

```text
SHA-256 e670aec336b9c7944ed51e03469d360623ea37efacde2950832ded8486fc8e61
```

The existing `/etc/registration.d/15_ssh_server` already registers
`/etc/init.d/service_sshd.sh`, so no registration binary was changed.

The new handler:

- waits for `br0`;
- copies the baked public key into `/var/config/meshscope-ssh`;
- creates a unique Ed25519 host key on first start;
- binds Dropbear to `br0`;
- disables passwords and local/remote forwarding;
- uses a PID file; and
- handles `sshd-start`, stop, restart, and LAN-status events.

The public key is device/operator-specific. A public image must never contain
a shared private key, shared host key, default password, or universal
authorized key.

### SquashFS compression constraint

The official `216903` filesystem uses XZ, 262,144-byte blocks, no tail-end
packing, and no xattrs. It has only 686 bytes of unused capacity in its
embedded UBI data LEBs.

A plain modern-XZ rebuild of the unchanged tree was 132,558 bytes larger than
the official filesystem and 131,872 bytes beyond the embedded capacity.
Repacking therefore requires deliberate,
kernel-compatible compression.

The official GPL kernel config contains:

```text
CONFIG_SQUASHFS_XZ=y
CONFIG_XZ_DEC_BCJ=y
CONFIG_XZ_DEC_ARM=y
# CONFIG_XZ_DEC_ARMTHUMB is not set
```

The safe rebuild must use only the ARM BCJ filter:

```sh
mksquashfs squashfs-root modified.squashfs \
  -noappend \
  -comp xz \
  -b 262144 \
  -no-tailends \
  -no-xattrs \
  -all-root \
  -Xbcj arm
```

Using `arm,armthumb` produces a slightly smaller image but is invalid for this
kernel because ARMTHUMB decoding is not enabled.

The modified filesystem result was:

| Field | Value |
| --- | --- |
| Exact SquashFS size | 30,049,118 bytes |
| SHA-256 | `79c45621b9710abfe48fafebf486f9c925bfaa3c0c6abda1a9b028ca430ff412` |
| Inodes | 5,457 |
| Data LEBs needed | 237 |
| Reduction versus official filesystem | 678,388 bytes |

### Rebuild the UBI

The `ubinize` volume configuration is:

```ini
[squashfs]
mode=ubi
image=modified.squashfs
vol_id=0
vol_type=dynamic
vol_name=squashfs
vol_size=76566528
vol_flags=autoresize
```

The matching command is:

```sh
ubinize \
  -o modified.ubi \
  -p 131072 \
  -m 2048 \
  -s 2048 \
  -O 2048 \
  -Q 1903991695 \
  ubinize.ini
```

The result contains two layout PEBs and 237 data PEBs. UBI Reader reports:

- no unknown or malformed blocks;
- the original image sequence;
- the original volume ID, type, name, alignment, autoresize flag, and
  603-LEB reservation.

### Reassemble the Linksys container

MeshScope now includes an offline-only assembler:

```sh
python3 tools/linksys_mx_repack.py \
  --original FW_MX4200_1.0.13.216903_prod.img \
  --ubi modified.ubi \
  --output FW_MX4200_1.0.13.216903_meshscope-ssh-poc.img \
  --expected-sku MX4200 \
  --expected-original-sha256 \
    b0a954835c879822fd1a2da23f09a6ec37da69914aacf07d8038b06fa02fad25
```

The tool:

1. verifies the original SHA-256 when supplied;
2. validates the MX4200 Linksys footer and its existing POSIX checksum;
3. validates every replacement UBI EC header;
4. preserves the original FIT prefix;
5. appends one erased trailer PEB;
6. preserves the footer metadata;
7. recalculates the eight-character POSIX checksum field; and
8. writes a new file atomically.

It has no MTD, SSH, HTTP, upload, or flash operation.

The proof output is:

| Field | Value |
| --- | --- |
| Size | 37,748,736 bytes |
| SHA-256 | `d07dff047e4010ec472a243c5c82454c8f1e31b666c6cb5f2768b2fb949d37a5` |
| UBI PEBs | 239 |
| UBI SHA-256 | `006fc7abda1df5d9b73022de1ef8b0a6a173e4515fbaff0435579c582edec2d1` |
| Footer checksum | `8F24B580` |

This exact proof output is intentionally not committed.

## Validation performed

The proof was checked through independent layers:

1. Feeding the unmodified official UBI through the new assembler reproduced
   the official `216903` IMG byte-for-byte, including its SHA-256.
2. UBI Reader parsed all 239 proof PEBs and reproduced the `squashfs` volume.
3. `unsquashfs` read the ARM-filtered filesystem and recovered:
   - the exact Dropbear SHA-256;
   - both multicall symlinks;
   - the service script with the expected SHA-256; and
   - the expected Ed25519 authorized-key fingerprint.
4. The OEM BusyBox shell accepted the service script with `sh -n`.
5. The actual stock `216903` `/usr/sbin/fwcc verify_signature` returned `0`
   for the proof IMG.
6. After one byte in the body was changed without updating the footer,
   the same `fwcc` returned `2`.

Because `/etc/fwcaps.sig` is absent, this build's updater follows the Linksys
footer magic/checksum path rather than requiring a GPG signature. The
unchanged FIT retains its original kernel and DTB hashes.

## Physical upgrade route

The local manual update page is:

```text
https://<node-ip>/fwupdate.html
```

Its authenticated multipart handler stores the upload, invokes
`update <uploaded file>`, and then runs `switch_boot_image`. Static scripts
show that the image is written to the inactive aggregate `kernel` or
`alt_kernel` MTD slot. The rootfs begins 6 MiB into that aggregate partition.

Before using a custom IMG:

1. verify the unit is MX4200 **hardware v1**; do not use this image on v2;
2. connect over Ethernet and disconnect WAN;
3. obtain and verify 3.3 V UART recovery;
4. record `/proc/mtd`, `/proc/cmdline`, `fw_printenv`, active
   `boot_part`, `boot_part_ready`, and `auto_recovery`;
5. back up `u_env`, both firmware slots, and `syscfg`;
6. verify the generated IMG hashes again;
7. test first on one recoverable non-gateway MX4200 Node;
8. keep the official image locally available;
9. observe the first boot over UART; and
10. verify SSH is key-only, LAN-only, and unreachable from WAN before
    upgrading any other Node.

If the modified slot boots but SSH fails, use the local web UI's restore
previous firmware operation. If it does not boot far enough to serve the UI,
use bootloader auto-recovery or UART to select the untouched slot. Those
recovery paths must be confirmed live before the first flash.

## Current decision

Both requested routes are technically possible:

- MQTT ACL is the shortest control path for Parent steering, but a stock ACL
  edit is too broad. Prefer a dedicated authenticated/TLS listener or a
  narrower SSH helper.
- The custom IMG route is now proven through rootfs, UBI, Linksys-container,
  and stock-updater validation. It is the most direct way to bootstrap SSH
  without exploiting a vulnerability, but it remains a physical-device
  experiment until slot geometry and UART recovery are verified.
